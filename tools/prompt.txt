Project repository: https://github.com/ExhataQ/ExhataQ (make sure it's public when sharing)

The project is an Electron music player. Source files live in Source/ organized into build/, src/, electron/, and tools/. When making changes, run Source/build/music_player.py which reads templates from build/, copies JS from src/js/, copies CSS from src/css/, copies Electron config from Source/electron/ into App/, copies font and icon assets from Source/tools/fonts/ and Source/tools/icons/ into the appropriate output locations, and generates output into App/MusicPlayerOutput/. The app is launched via App/electron.exe.

AUDIO FILE PROCESSING ARCHITECTURE:

Source/electron/scan-folder.js (RUNTIME PHASE):
- Node.js script using music-metadata library
- Gets copied to App/scan-folder.js during build
- Handles ALL audio scanning: importing dropped files, changing music folders, download-and-scan, rebuild-from-folders
- Runs as Electron child process when users interact with the running app
- Editable file ✓

Source/build/music_player.py (BUILD PHASE):
- Python script that does NOT do metadata scanning
- Only preserves song data from previous App/MusicPlayerOutput/player.js and re-injects into regenerated output
- Editable file ✓

Dual-update rule applies only within scan-folder.js changes. If you need to change supported formats, cover extraction, metadata fields, duration formatting, cover hashing, or file URL handling, update scan-folder.js only.

Electron main-process structure: main.js owns IPC registration and application bootstrap, including the first-run welcome-select-folder flow and online-lyrics IPC; window-manager.js owns the main window and window-state persistence; loading-window.js owns the scan/loading progress window; scanner.js owns shared scan-process execution, progress handling, result parsing, and scan-result merging while preserving the behavior of each scan entry point; music-folders.js owns music-folder configuration and folder metadata operations while main.js retains scan and loading-window orchestration; downloads.js owns download-folder configuration and remote file downloading while main.js retains IPC and delegates the downloaded file to scanner.js for scanning and merging; file-operations.js owns lyrics file dialog and filesystem operations and gets the main window from window-manager.js.

Note: fonts are self-healing. Source fonts live in Source/tools/fonts/ and are copied to App/MusicPlayerOutput/fonts/ on every build. If any font file is missing from both, music_player.py downloads them from CDN. all.min.css paths are rewritten from url(../webfonts/...) to url(...) after download.

Source/src/css/ contains:

music-folders.js — Music-folder configuration reading/writing plus pure folder validation/removal/song-count helpers. Path comparison uses Windows normalization; song counts require the song path to be inside the folder rather than merely sharing a string prefix.
online-lyrics.js — LRCLIB API client for the Electron main process. Builds exact-match (/api/get) and broad-search (/api/search) requests, retries transient HTTP errors with backoff, de-duplicates the exact match out of the search results, and returns { exact, results }. Provides downloadLyricsFile for saving LRC or plain lyrics into the configured download folder with collision-safe filenames. Exposes searchLyrics and downloadLyricsFile.

Online lyrics result behavior:
- LRCLIB online search uses the exact /api/get result as the first result when available, then includes other /api/search matches after it, de-duplicated by LRCLIB id or matching track/artist/duration. Temporary HTTP/network failures are retried with short backoff delays; exact-match failure does not block the broader search. If artist/title/album fields are incomplete, the search uses LRCLIB's broad q query so a single populated field can still return results.
- The Online Lyrics view displays 10 results per page with Previous/Next navigation. LRCLIB currently returns a maximum of 20 search results and does not support server-side pagination, so the renderer paginates the returned result set locally.
- Pagination resets to page 1 whenever a new online lyrics search starts, and changing pages clears the expanded result selection.
- A collapsed result card opens on any click inside the card; an expanded card can only be collapsed by clicking its chevron. Badge buttons (Synced LRC / Lyrics) switch the active type without collapsing the card.
- The expanded card's primary action depends on how the view was opened. Opened from the header (fromHeader true): the button reads Save LRC to a song or Save Lyrics to a song and opens the song picker. Opened from the lyrics view (fromHeader false): the button only appears once the search fields have diverged from originalQuery, and reads Use LRC for this song or Use Lyrics for this song, attaching directly to the playing song.
- The song picker is a modal overlay with a prefilled search input (LRCLIB track title plus artist name) and a scrollable list of getActiveSongs() filtered by title, artist, or album substring. Picking a song attaches the LRC or plain lyrics to it and closes the picker. The list uses the app's custom scrollbar.

Online lyrics: The global header can open the online lyrics view before the regular Lyrics view has been visited, so the online lyrics renderer initializes its own lyrics-view-root when needed.

Metadata editor:
- `src/js/20-metadata-editor.js` provides the right-panel Metadata editor view.
- The edit button beside the Info title opens Metadata; the Metadata view has a back control to return to Info.
- `electron/metadata-editor.js` and `electron/metadata-editor.py` read/write common audio tags through Python mutagen.
- Saved metadata is written to the audio file and mirrored into deployed `MusicPlayerOutput/player.js` so library data remains current.

- `src/js/20-metadata-editor.js` provides the right-panel Metadata editor view, loads existing file tags into the editor, supports editing/saving, and supports ExhataQ JSON metadata import/export.
- `electron/metadata-editor.js` and `electron/metadata-editor.py` read/write common audio tags through Python mutagen; the writer uses the destination audio format so imported ExhataQ JSON can be applied across supported audio types.
- `electron/main.js` and `electron/preload.js` expose metadata read/write and ExhataQ JSON import/export IPC operations, including native file dialogs for JSON files.
- Metadata editor opens without a loading message and initially renders metadata already available on the selected song; direct audio-tag reading then refreshes it when successful. Scanner aliases titleSort/artistSort/albumSort/encoder are mapped to the editor fields.
- Metadata import/export uses ordinary .json files; the JSON payload remains versioned but the filename extension is standard JSON.

- Metadata editor loads initial song metadata immediately and supplements it asynchronously from the audio file without clearing non-empty values or rebuilding the form.
- `electron/metadata-editor.py` detects ID3 through the loaded tag object (`audio.tags`) and writes MP3 fields as proper Mutagen ID3 Frame instances; non-ID3 formats use their native tag mapping.
